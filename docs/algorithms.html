Version 1 (original)
  • Priority = Risk Score / Effort, nothing else.
  • Full table sorted on every page load to show five rows: O(m log m).
  • Category and compliance status ignored.
Final version
  • Weighted score using category weight and status multiplier.
  • Bounded min-heap keeps only the top n: O(m log n).
  • Deterministic tie-breaks, checked against a full sort in tests.

Artifact description

The artifact is the same Cloud Security Risk Assessment Tool. Version 1, built in September 2026, ranked findings with one formula, Risk Score divided by Effort, and found the top five quick wins by sorting the whole findings table each time the Priority Dashboard loaded. This enhancement replaced both.

Justification for inclusion

Ranking is the reason the tool exists. If the wrong control is at the top of the list, nothing else in the app matters. That made ranking the right place to show algorithmic thinking on a real problem instead of an isolated exercise. The work lives in ranking.py.

  • Bounded min-heap for top-N. get_top_priority_controls keeps at most n items in a heap while it scans the findings. The root is always the worst item kept, so each new finding is compared once and, if better, replaces the root in O(log n). The total cost is O(m log n) instead of the full sort's O(m log m).
  • Weighted priority score. calculate_weighted_priority_score multiplies the base score by a category weight and a compliance-status multiplier. An identity and access gap weighs 1.3 and a governance gap 0.7. A non-compliant control keeps its full score, a partial one keeps 60 percent and a compliant one keeps 10 percent, because compensating controls can still fail.
  • Deterministic order. Ties are broken by Risk Score and then by control name, so the same data always gives the same list.

The skills shown are complexity analysis, heap data structures, tie-breaking design and testing an optimized algorithm against a simple reference version.

Reflection

My first heap version negated the scores so Python's min-heap would act as a max-heap, which is the usual trick. A test showed that it returned the wrong controls. For a bounded top-N heap I needed the opposite: the root has to be the worst item kept, so it can be evicted cheaply. Finding that bug through a test, not by reading the code, showed me why a cross-check against a plain sort is worth writing.

In the final review I found a second bug. When two controls tied exactly at position n, the heap used input order to choose between them, so it could keep "Zebra" and drop "Alpha" while a full sort would do the reverse. My random cross-check had not caught it because its decimal scores almost never tied. I fixed the heap key so it compares names in reverse order, and I added two regression tests. One of them uses small integer scores so ties happen in most runs. The lesson is that a test only proves what its data exercises.

The main trade-off is honesty about the weights. They are my estimates from common incident patterns, not a model fitted to incident data, and the code says so in a comment next to them. Calibrating them against real data is future work and part of the research paper I plan to write from this project.
