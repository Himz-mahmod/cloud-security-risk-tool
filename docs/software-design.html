Enhancement 1

Software design and engineering

Turning a working prototype into software that checks who is using it, refuses bad input and tests itself.

Version 1 (original)
  • No login. Anyone with the link could change data.
  • Input saved as entered. The same control could be assessed twice.
  • Scoring and validation mixed into page code.
  • No automated tests.
Final version
  • Login gate with salted PBKDF2 password hashes.
  • UI-independent validation and duplicate checks in validators.py.
  • Every finding records who assessed it.
  • 102 pytest tests, run by GitHub Actions on every push.

Artifact description

The artifact is the Cloud Security Risk Assessment Tool, a Python and Streamlit web application for small organizations that run Linux-based cloud infrastructure. A user scores each security control on likelihood, impact and implementation effort, and the tool ranks the controls so a small team knows what to fix first. I built Version 1 in September 2026, during CS 499, as the baseline for this portfolio. It had four pages, stored findings in a CSV file, had no login and no tests, and fit in two Python files.

Justification for inclusion

I chose this artifact because it solves a problem I see at work: small teams face long lists of security findings and no clear order to fix them in. A security tool that is itself insecure would undercut its own purpose, so software design and engineering was the right first enhancement.

The enhancement added four components:

  • auth.py stores passwords as salted PBKDF2-HMAC-SHA256 hashes with 100,000 iterations and verifies them with hmac.compare_digest, a constant-time comparison. The app shows a login screen before any page.
  • validators.py checks score ranges, control names, categories, statuses and duplicates. It does not depend on Streamlit, so the same rules apply wherever data comes from.
  • tests/ holds a pytest suite. It started with 33 tests in this milestone and has 102 in the final version.
  • .github/workflows/tests.yml runs the full suite on GitHub Actions on every push and pull request to main.

Before the enhancement, anyone could open the app, save any value and assess the same control twice. Nothing recorded who entered a finding. After it, every user logs in, every finding records who assessed it, and bad input is refused with a clear message. The skills shown are modular design, secure password storage, defensive validation, test automation and continuous integration.

Reflection

The biggest lesson was that code is only as testable as its structure allows. Streamlit reruns the whole script on every click, so logic inside the page code is hard to test. Moving validation and scoring into plain modules made them easy to test and easier to read. Login state was a related challenge. Because the script reruns, I had to keep the logged-in user in st.session_state and check it at the top of every run.

I was also new to Git, and I work on Windows. Learning to commit, push and read a failed CI run took real time, but now a green check on GitHub tells me and any reviewer that the code still works. I followed the plan from my code review closely, and I used my instructor's feedback on each milestone to improve the next one. In the final version I added the untouched Version 1 code to an original folder, so a reviewer can compare before and after directly.
