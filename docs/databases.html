Artifact description

The artifact is the Cloud Security Risk Assessment Tool. Version 1, built in September 2026, saved every finding to findings.csv, and the Milestone Two version added a users.json file for accounts. This enhancement replaced both files with a SQLite database.

Justification for inclusion

My code review found four problems with flat-file storage. Nothing linked a finding to its control or to the user who entered it. Every save rewrote the whole file, so two saves at once could lose data. Every filter scanned every row. The storage layer accepted any string in any column. A risk register that can silently lose or corrupt findings cannot be trusted, so storage needed a real database.

  • Schema. Three tables, users, controls and assessments, linked by foreign keys that are switched on for every connection.
  • Constraints. CHECK constraints on likelihood (1 to 5), impact (1 to 5), effort (1 to 3), status, risk score and priority level. UNIQUE constraints stop a control from being assessed twice.
  • Indexes on the weighted score, priority level, category and assessor, which are the columns the pages filter and sort by.
  • Safe queries. Every value is a bound parameter. ORDER BY cannot take a parameter, so list_assessments picks the sort order from a fixed whitelist.
  • Migration. migrate_csv_to_sqlite.py imports the old CSV and JSON data in one transaction, recomputes scores instead of trusting the file, skips and counts bad rows, and is safe to run twice.

I chose SQLite over a database server because the target user is a small team that wants one file and nothing extra to run. SQLite gives up concurrent writes from many machines, which this tool does not need, and keeps the integrity features it does need. The skills shown are relational schema design, data integrity constraints, indexing, injection-safe queries, transactional data migration and benchmarking.

Reflection

I learned to measure before I claim a speed-up. benchmark_indexes.py generates 50,000 rows and times queries with and without the indexes. The top-five query ran about 1,900 times faster with its index. The priority-level filter improved only about three times, because that column has just four values, so the index narrows the search far less. I would not have predicted that difference without measuring it.

Real files caused the hardest problems. CSV files saved by Excel can start with a byte-order mark, use Windows line endings or use semicolons as delimiters, and my first importer failed on all three. I added handling and a test for each case. Testing also exposed a commit in the middle of the migration: creating the default admin account committed the transaction early, so a later failure could leave half the data behind. I added a commit=False option and a test that forces a failure and checks that nothing was written.

My instructor's feedback on an earlier milestone, that its narrative was missing, taught me to check the whole submission package and not only the code. For the final version I added a schema diagram to this page, added the original Version 1 code to the repository and checked every claim in this narrative against the code and test output. Two limits remain: the app cannot yet edit or delete a single assessment, and the PBKDF2 iteration count should rise to the 600,000 that OWASP currently recommends.

Course outcomes.

  • Outcome 5 (security mindset): met. Parameterized queries, the ORDER BY whitelist and database-level constraints defend against injection and bad data.
  • Outcome 4 (techniques and tools): met. Transactions, indexes, a repeatable migration and benchmarks are standard database practice.
  • Outcome 3 (design trade-offs): met. The SQLite choice and the index results are measured and explained.
  • Outcome 2 (communication): met. The README and this page document the schema for other developers.
  • Outcome 1 (collaborative environments): supported. Constraints protect the data even from a teammate's future code that skips validation.
